# strongSwan: customer side of the VPN Site-to-Site tunnel

This folder configures a Linux host (Ubuntu 22.04 / 24.04) in the data center as the IPsec peer of the
**GreenNode VPN Site-to-Site** gateway. Any IKEv2-capable device works instead (pfSense, FortiGate,
Palo Alto, ...): see [Other gateways](../README.md#other-gateways-pfsense-fortigate-palo-alto).

| File | Purpose |
|---|---|
| [`swanctl.conf`](swanctl.conf) | IKEv2 connection `greennode-vpn` with child SA `greennode-vpc` (proposals, traffic selectors, DPD) |
| [`greennode.secrets.conf.example`](greennode.secrets.conf.example) | Template for the pre-shared key file (never commit the real one) |

## 1. Collect the values (all examples must be replaced)

| Value | Where it comes from | Example used in the files |
|---|---|---|
| GreenNode VPN public IP | VPN detail page in the GreenNode console (vNetwork, VPN Site To Site) | `203.0.113.10` |
| On-prem gateway public IP | The IP you entered as **Remote Public Gateway IP** when creating the VPN | `198.51.100.20` |
| On-prem LAN CIDR | The **Remote Private CIDR** you entered | `192.168.0.0/16` |
| Customer VPC CIDR | The VPC selected in the VPN configuration | `10.20.0.0/16` |
| Pre-shared key | The key you typed or the one generated by GreenNode (must be identical on both sides) | none |
| IKE / IPsec policy | **Algorithm Configuration** of the VPN; read the final values on the VPN detail page | see `swanctl.conf` |

The on-prem CIDR must not overlap the customer VPC CIDR or `172.30.0.0/16` (GreenNode rejects overlapping CIDRs:
error codes 2017 and 2023 in the VPN connect conditions).

## 2. Install strongSwan (Ubuntu)

```bash
sudo apt update
sudo apt install -y strongswan-swanctl charon-systemd
systemctl list-unit-files | grep -i strongswan          # confirm the unit name (normally strongswan.service)
sudo systemctl enable --now strongswan
```

## 3. Kernel settings

Required only when this host forwards traffic to a separate MCP host (gateway topology). It does no harm in the
all-in-one topology.

```bash
sudo tee /etc/sysctl.d/99-ipsec.conf >/dev/null <<'EOT'
net.ipv4.ip_forward = 1
net.ipv4.conf.all.send_redirects = 0
net.ipv4.conf.all.accept_redirects = 0
EOT
sudo sysctl --system
```

## 4. Install the configuration

```bash
sudo cp swanctl.conf /etc/swanctl/swanctl.conf
sudo cp greennode.secrets.conf.example /etc/swanctl/conf.d/greennode.secrets.conf
sudo chown root:root /etc/swanctl/conf.d/greennode.secrets.conf && sudo chmod 600 /etc/swanctl/conf.d/greennode.secrets.conf
sudoedit /etc/swanctl/swanctl.conf                      # addresses, ids, CIDRs
sudoedit /etc/swanctl/conf.d/greennode.secrets.conf     # the real pre-shared key
```

A pre-shared key that contains quotes, backslashes or other special characters is safest hex encoded: write
`secret = 0x<hex>` with `printf '%s' "$PSK" | od -An -v -tx1 | tr -d ' \n'` (the `lab/` script does this).
A copy kept inside this repository folder as `*.secrets.conf` is git-ignored.

## 5. Start and verify

```bash
sudo swanctl --load-all                                 # loads connections and secrets; start_action=start starts the tunnel
sudo swanctl --list-sas
```

Do not also run `swanctl --initiate`: `start_action = start` already negotiates the tunnel when the configuration is
loaded and keeps retrying (`keyingtries = 0`) while the GreenNode VPN is not `Active` yet, so a second initiate would race
with it and can leave a duplicate SA.

A healthy tunnel shows `ESTABLISHED` for the IKE SA and `INSTALLED, TUNNEL` for the child SA, with the expected
traffic selectors:

```
greennode-vpn: #1, ESTABLISHED, IKEv2, ...
  local  '198.51.100.20' @ 198.51.100.20[4500]
  remote '203.0.113.10' @ 203.0.113.10[4500]
  AES_GCM_16_256/PRF_HMAC_SHA2_256/MODP_3072
  greennode-vpc: #1, reqid 1, INSTALLED, TUNNEL, ESP:AES_GCM_16_256
    local  192.168.0.0/16
    remote 10.20.0.0/16 172.30.0.0/16          # may be narrowed to 10.20.0.0/16 by GreenNode
```

More checks:

```bash
sudo journalctl -u strongswan -f                        # negotiation log (proposal mismatch, PSK errors)
ip xfrm policy                                          # installed IPsec policies
ping -c3 <an IP in the customer VPC>                    # from the MCP host / gateway, once the VPC routes exist
```

| Symptom in the log | Meaning |
|---|---|
| `NO_PROPOSAL_CHOSEN` | IKE or ESP proposals do not match the GreenNode policy: align `proposals` / `esp_proposals` with the VPN detail page |
| `AUTHENTICATION_FAILED` | Pre-shared key or ids differ |
| `TS_UNACCEPTABLE` | Traffic selectors differ: local_ts must be the **Remote Private CIDR** you entered in the console |
| No response at all | UDP 500/4500 blocked, wrong peer IP, or the GreenNode VPN is not `Active` |

## 6. Routing inside the data center

The MCP host must send replies for `10.20.0.0/16` (customer VPC) and `172.30.0.0/16` (AgentBase) back to the
tunnel endpoint:

- Same host as strongSwan: nothing to add (strongSwan installs the policies and routes).
- Separate MCP host: add the routes on the MCP host or on the data-center router, next hop = the strongSwan host
  (example `192.168.10.1`):
  ```bash
  sudo ip route add 10.20.0.0/16 via 192.168.10.1
  sudo ip route add 172.30.0.0/16 via 192.168.10.1
  ```
  Make them persistent with netplan or your network manager.

Then apply the firewall: [`../firewall/nftables.conf`](../firewall/nftables.conf).
